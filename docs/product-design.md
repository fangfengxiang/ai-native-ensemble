# Ensemble 产品设计与讨论记录

版本：V0.2 · 2026-11-02。本文与原型共同维护，区分已明确方向、设计建议与待确认事项。当前为产品设计阶段，不代表平台能力已经实现。

## 1. 定位与愿景（已明确）

AI 原生协作交付系统：基于 AI Native 理念重塑软件交付工作流，构建人机协同的自动化端到端交付系统。重点是开发交付平台，测试是交付链路的必要环节。

放大工程师能力，减少重复编码和信息协调，使其更多参与业务域决策、产品打磨以及如何让 AI 更好服务业务。更快响应一线真正需要 IT 支撑的问题。

自动化不能带来低价值需求泛滥、代码审查拥堵、重复建设与系统无序。交付速度需与业务价值、稳定性和长期维护成本共同衡量。

## 2. 已知困境

业务提需随意、信息不完整；部分诉求是使用问题、已有能力或已有规划，部分超出业务域边界，部分牵涉多个系统。影响范围和历史规则难以在早期看清。

业务到产品再到研发的多次转述造成信息耗损。技术评审才发现范围、周期或历史规则冲突，导致返工。PRD 静态图片难以完整表达业务预期，产品耗费大量时间做翻译与消息传递。

## 3. 需求澄清与业务确认（已明确）

1. 产品结合本业务域制定提需模板与规范。
2. AI 从自然语言诉求引导业务补充背景、现有业务流程、目标、价值和期望变化。
3. 补充系统现状、已有功能与规划、领域规则、初步影响范围和潜在冲突；领域研发在需要时提前参与。
4. 形成可留存的业务需求工单，由业务线产品审核决策。

设计建议：降低起步门槛，渐进补齐信息；保留业务原始表达，区分有来源的事实、AI 推断和待确认信息。标准化的目的在于共享理解，不是最大化文档数量。AI 不能代替业务确认价值或研发确认系统事实。

候选决策分流：补充信息、复用已有能力、合并规划、进入方案评估、暂缓。审核是否同时包含资源承诺和排期尚未明确。

## 4. 产品规划（已明确方向）

产品利用提前获得的业务系统上下文做决策，AI 辅助检索背景和领域知识，领域研发按需确认约束。早期参与减少后期打回，但不保证消除所有技术不确定性。

通过可交互 HTML 快速向业务演示并对齐期望。产品阶段输出三类产物：

| 产物 | 内容与作用 |
| --- | --- |
| 交互原型 HTML | 与业务对齐的页面、操作路径及反馈状态 |
| 产品设计 MD | 背景、价值、功能点、范围与设计思路 |
| 功能规则 MD | 原型每个功能点的规则、权限、边界及异常补充 |

产品作为项目 Owner，更多从整个系统与产品全局做取舍，拒绝无收益需求、改善体验，减少来回转述。Owner 的具体权限与其他角色的责任边界仍需细化。

建议：三类产物用稳定功能编号互相关联；确认版本后记录变更原因和影响，避免三份材料各自漂移。原型不能代替完整的规则说明和验收标准。以上关联机制尚未定稿。

## 5. 产品主导轻量交付

用户提出的方向：允许部分纯前端改动由产品接管，直接进入 Coding Agent 开发后交付测试，不经过常规研发环节。

待确认的建议：按风险和实际改动范围决定准入，而非只看前端文件。局部文案、样式与既有组件的受限复用可作为候选；权限、交易规则、接口契约、公共组件、依赖与构建变更应转研发评估。

建议执行方式：产品定义范围 → 准入判断 → Agent 在真实仓库的隔离环境修改 → 检查实际改动和验证证据 → 产品确认体验 → 交付测试。发生越界时带上下文转研发。原型 HTML 不直接视为生产代码。

合并、测试放行、生产发布的责任人及权限尚未确定，不能据此理解为产品可自动发布任何前端改动。

## 6. 研发阶段：仅记录现状，等待补充

用户描述的传统流程：需求评审 → 架构分析 → 数据建模 → 前端与后端工程师开发 → 部署测试环境、前后端联调 → 自测 → 修复 → 开发周期结束 → 进入测试阶段。

按用户要求，暂不展开此阶段的问题分析或冻结目标流程，等待进一步补充。原型中既有的后续执行与验证阶段是概念性候选方案。

## 7. 系统全景与 QoderWake 的关系

业务、产品、领域研发与交付质量角色围绕共同的工单和产物协作。平台拟组织长期运行的交付任务、Agent 协作、上下文与规范，连接需求规划、文档、代码、接口依赖和 CI 等现有系统。

QoderWake 的角色、群组、流程编排、触发、人工介入以及 Skills、连接器与权限等能力作为参考基础。具体 API、部署方式、仓库操作、执行隔离和回调能力需技术验证，当前没有完成集成。

HelixHarness 提供工程知识、约束、规格与检查规则组织方式的借鉴；黑夜路人的组织转型讨论用于校准开发平台定位。不能将参考产品宣传或行业案例直接当成本平台的已实现能力和收益承诺。

## 8. 协作与岗位重塑

业务负责问题真实性和结果确认；产品负责价值取舍与整体体验；研发负责系统事实、架构边界与关键技术判断；质量角色负责验证设计和关键质量判断。AI 承担信息整理、追问、检索、明确任务执行及证据汇总。

建议补充的原则：产物应可追溯与可验证；按风险分配自动化权限；减少无意义交接；知识注明来源、适用范围与维护责任；保留人工纠偏和异常接管能力。

## 9. 实施与收益验证（建议，未承诺周期）

先选择一条业务链，验证需求澄清与决策，再扩展产品规划和受限 Agent 执行，最后扩大跨岗位协作与反馈闭环。试点业务、时间、人力和技术方案尚未确定。

观察澄清周期、理解偏差返工、复用与重复需求合并、人工执行及协调时间、需求到可用交付周期。同步观察业务填写负担、审查积压、线上缺陷、变更失败与维护成本，不用生成代码量或 Token 消耗单独代表价值。
