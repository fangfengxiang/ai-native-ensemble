# Ensemble PRD 产品评审与后续规划

评审日期：2026-11-03。依据：main 的 68b2f8669b3551cf404b76845298b6637d1fa511，包括产品设计记录与 V0.4 原型源码。范围为产品方案、流程与落地条件；未进行浏览器操作、真实用户访谈或界面可用性测试。本文均为评审建议，待项目 Owner 确认后再纳入正式需求。

## 1. 总体判断

当前材料已经形成有方向的产品愿景和流程设计，适合业务、产品、研发共同讨论；还不足以让团队直接按完整平台进入开发。主要缺口是首批服务对象与场景、明确的阶段完成条件、可回退的状态流转、产物版本关系、执行能力接入边界和真实收益基线。

最有价值的定位是：让业务意图、系统事实、产品决策与研发执行在同一条交付记录上连续发生，减少反复理解与无效等待。愿景可以覆盖全链路，首个试点必须选择一条可重复、可验收的真实交付路径。

保留的核心判断：以开发交付为中心；产品主导价值与体验；领域研发在关键事实处提前参与；测试与审查提供交付证据；不以代码量或请求处理量单独证明平台价值。

## 2. 需要修正或补足的产品判断

### 2.1 标准化有价值，不能只增加文档工作

规范化能减少缺失信息，但文档数量增加不等于沟通更有效。AI 应复用已经确认的事实、发现前后不一致、定位需要谁作决定。下一轮应验证一次变更如何同时影响原型、规则、验收和执行任务，避免产品分别维护三份副本。

### 2.2 交互原型是对齐工具，确认动作需要具体依据

业务点击“确认”不能证明业务流程已被理解。至少围绕一条核心业务路径、一个例外情况和明确的预期结果确认。权限、数据约束与技术可行性需要单独说明，不能从可点击页面推导。原型完成与产品包可交接是两个不同的里程碑。

### 2.3 技术事实应前置，研发参与强度需要按问题分配

每条诉求都开一次完整技术评审，会把等待前移。先检索有来源的现有能力和规则；只有遇到跨系统、规则冲突、事实缺失或超出约定边界时，再请求相应领域研发参与。试点时维护小范围可靠知识，比搭建完整企业知识库更重要。

### 2.4 产品 Owner 要有决策权，也要避免成为新的单点

产品可负责价值、范围、优先级和体验；系统事实、技术边界、代码合并和生产发布需要对应责任人。确认方式应能处理委托、补充、退回和等待。已有规则覆盖的日常事项可以采用轻量处理，例外升级给产品或领域负责人。

### 2.5 “纯前端”不足以作为自动交付准入标准

建议对一类明确变更建立试点白名单，并检查 Agent 的实际修改是否仍在边界内。权限、关键业务计算、接口契约、公共组件或依赖变动需要重新判断。产品验收体验不能替代工程检查；测试人员的工作量也应纳入整体人效。

### 2.6 价值不明确不等于没有价值

稳定性、必要的架构维护和风险降低可能无法用短期收入衡量。建议把价值拆成效率、业务增长、体验、稳定性与必要治理等类型，记录证据、紧迫性和可信程度。证据不足的诉求可先小范围验证，不要求业务编造精确 ROI。

## 3. 从愿景稿到可开发 PRD 的优先缺口

| 优先级 | 当前依据 | 缺失及影响 | 下一份需要补齐的内容 |
| --- | --- | --- | --- |
| P0 | 定位覆盖业务、产品、研发和质量 | 首批主用户与使用场景未锁定，难以决定先做什么 | 一个业务域、一套系统、一类首批变更、产品及领域负责人 |
| P0 | 需求决策与产物已列出 | 谁能推进、退回或结束，完成依据不清楚 | 关键状态、动作、责任人、必要输入和完成条件 |
| P0 | 三类产品产物 | 原型、规则和后续任务可能对应不同版本 | 同一个产品包的版本、业务确认记录、变更影响规则 |
| P0 | 拟基于 QoderWake | 能发起任务不代表能实现完整的平台内运行管理 | 最小接入验证：启动、查状态、人工交接、产物定位、失败及重复请求 |
| P1 | 领域知识与事实来源 | 事实维护、有效范围与未确认状态未细化 | 小范围知识清单、来源、维护人、适用版本及纠错入口 |
| P1 | 六个讲解章节与固定示例 | 方案容易理解，实际工作台中的操作还未设计 | 围绕一条真实需求的详情工作台 |
| P1 | 已列效率与质量指标 | 缺少基线、口径和试点验收门槛 | 历史样本、可比新样本、总体人时和审查负担记录 |

这里的优先级是规划建议，不构成已确定的开发排期。

## 4. 建议先确定的产品对象和完成条件

先组织四类核心记录，避免通过聊天记录猜测当前进度：

| 记录 | 最小需要表达 |
| --- | --- |
| 需求工单 | 原始问题、业务场景、价值证据、范围、责任人、当前处理路径 |
| 产品包版本 | HTML、产品设计与功能规则对应的同一版本，验收条件及未决项 |
| 决策记录 | 谁基于哪个版本作出何种决定，依据和下一责任人 |
| 执行 Run | 使用哪个已确认产品包版本、当前状态、实际产物、验证结果与人工待办 |

知识来源可以先以工单中的引用维护，无需立即建成独立复杂模型。

建议的阶段完成条件：

- 可决策：问题、预期结果与价值依据足够，相关系统事实及未知项已明确。
- 产品包可交接：业务已确认关键体验，产品确认范围；规则与验收完整到下游可执行；尚有重大未决项时不能伪装为准备就绪。
- 执行结束：产物存在且能访问，包含实际改动与验证证据。Agent 报告完成本身不代表验收。
- 交付完成：对应责任人完成独立验收，并保留实际交付位置与结果。
- 复用、合并、暂缓与不予推进也应有明确结论、依据和后续责任，不能都停在“处理中”。

业务处理状态与 Agent 运行状态分别表达。例如“等待业务确认”是需求推进状态，可能对应多个已结束的 Agent 任务。输入或范围改版时记录旧版本的执行，不把旧结论直接套到新版本。

研发阶段的详细流程仍等待用户补充；这里仅规定上下游需要看见的输入、结果和责任。

## 5. Ensemble 与 QoderWake 的建设边界

建议 Ensemble 自己组织：业务域入口与提需模板、已有能力与产品规划关联、产品取舍及价值记录、产品包版本、交接责任、业务验收和整体交付度量。

QoderWake 已有 Waker、资源配置、WakerFlow、人工确认、运行记录和触发等能力，可优先复用。通用的角色管理、流程画布和运行日志，不宜在首版同时再建一整套。

P0 接入验证至少回答：

1. 从一条业务工单能否准确发起目标 Waker 或流程，并定位这一次执行？
2. 等待输入、失败、部分失败和完成，能否被平台正确呈现？无法通过接口处理的环节能否可靠跳转到原产品？
3. 人工确认操作是否有可用的集成接口，还是需要人在 QoderWake 中完成？
4. 最终文件、分支或其他产物如何返回并绑定产品包版本？
5. 重复触发、超时、取消和输入变化后重跑，如何避免重复写入或复用旧结论？

官方文档确认了 API 触发，但这不构成全部接口已覆盖的证明。尤其是会话复用标识并非幂等键，请求已接受也不等于工作已完成；调用方仍需处理重复请求。WakerFlow 终止不会自动撤销外部变更，输入或定义改动后的再执行也要区分临时故障重试与新运行。

HelixHarness 可借鉴上下文、规格和检查规则的组织方式。其当前宿主支持及可选框架评测平台有明确范围，不能据此认定可直接作为 QoderWake 插件或通用代码质量评测服务。

## 6. 建议的 MVP 与分批规划

首个完整验证目标：一个业务域、一个项目、一类边界明确的变更，从业务问题推进到经业务确认的产品包，再到可审查变更和独立验收。需求处理前半段可以先交付，但端到端价值需在后半段也跑通后验证。

| 批次 | 交付重点 | 进入下一批的依据 |
| --- | --- | --- |
| P0 场景与能力验证 | 选试点；复盘约 5—10 个历史案例；明确责任与价值类型；验证 QoderWake 最小接入链路 | 有完整真实案例、基线和明确接入边界；关键能力有实测证据 |
| P1 需求到产品包 | 单域模板、AI 澄清、事实引用、产品分流、交互原型、三类产物与确认版本 | 业务与下游能理解并使用产品包；高频补充和返工原因可识别 |
| P2 首条受控交付链 | 选定变更类型；绑定产品包启动 Agent；形成实际差异、验证证据、人工待办与验收结论 | 独立验收通过；总体人工时间改善；审查积压与稳定性无明显恶化 |
| P3 团队复用 | 扩大同类案例；维护知识和模板版本；再扩第二业务场景 | 连续批次有效；复用成本、运行成本与知识维护负担可接受 |

样本数是便于启动的建议，不是统计显著性保证。先以案例验证工作方法，再在可比任务中持续观测；未确定团队投入前不承诺日期或提升比例。

首版应围绕一条真实交付链做深；复杂跨域依赖图、通用工作流设计器和大范围自动扩展留待试点证明需要之后。

## 7. 如何判断价值真的发生

| 观察项 | 建议口径 | 防止误判 |
| --- | --- | --- |
| 业务交付周期 | 首次提交到独立验收，按任务类型和复杂度比较中位数及较慢任务 | 包含等待时间；暂缓、拒绝与复用单独分析 |
| 总人工投入 | 业务、产品、研发、测试的实际投入及返工 | 不能只减少产品时间却把负担转给研发或测试 |
| 产品包交接质量 | 首次交接无需关键背景补充的比例及退回原因 | 由下游参与评价，不能只由生成者自评 |
| 审查与稳定性 | 审查等待、返工、缺陷及变更失败 | 减少检查本身不计为效率收益 |
| 单次成功交付成本 | 包含失败尝试的执行成本和人工投入 | Token 量不作为独立绩效指标 |
| 业务结果 | 交付后是否解决原问题，例如实际处理耗时或操作错误减少 | 不以需求量、产物数量或生成代码量代替价值 |

## 8. 下一版原型优先画什么

现有六个 Tab 适合作为方案说明。建议下一步围绕一个真实案例制作「需求详情工作台」，让业务、产品与研发都能回答：当前卡在哪里、证据是什么、谁需要决定、下一步可做什么。

首屏展示业务问题、价值依据、当前状态、责任人和下一动作。详情组织事实与来源、候选路径及决策、交互原型、功能规则、产品包版本，以及与该版本关联的执行及验收证据。

先演示五种情形：新诉求不完整、已有能力可复用、跨系统事实冲突、业务确认后范围变化、受限前端改动中 Agent 越界。每一种都需要可见的处理路径和责任。该工作台属于建议中的下一版范围，尚未实现。

下一轮最值得补充：第一条试点业务链、产品与领域研发的现有决策权、研发阶段最典型的返工和等待案例。
